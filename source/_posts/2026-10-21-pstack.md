## 🧅 pstack：先寫深，再平行開 Agent

**✅ 這篇做什麼：整理 [cursor/plugins](https://github.com/cursor/plugins/tree/main/pstack) 裡的 pstack。作者是 Lauren Tan（poteto）。她的說法很直：AI 產出的程式太容易又長又鬆，pstack 是她在 Cursor 每天用來把工作做深、做少、再敢平行開 Agent 的那組 skills。**

<!-- more -->

plugin.json 寫的版本是 0.15.29，授權 MIT。描述只有一句：想快，先走深。目標不是把行數衝高。

倉庫在 `pstack/`，旁邊還有給 Claude Code 用的產生副本 `harness/pstack/`。改完 pstack 本體之後，要在倉庫根目錄跑 `node scripts/generate-pstack-harness-trees.mjs`，把產生結果一起提交，不然 CI 會因為副本過期失敗。

---

# 🛠️ 怎麼裝

在 Cursor 裡：

```text
/add-plugin pstack
```

在 Claude Code 裡：

```text
/plugin marketplace add cursor/plugins
/plugin install pstack@cursor-plugins
```

Claude Code 會替指令和 agent 加上外掛前綴，所以 `/poteto-mode` 變成 `/pstack:poteto-mode`。對照表在 [claude-code adapter](https://github.com/cursor/plugins/blob/main/pstack/docs/harness/claude-code.md)。`/pstack:setup-pstack` 會把模型選擇寫到 `~/.claude/rules/pstack-models.md`。Bugbot、Automations 這類 Cursor 才有的步驟會跳過，並留一行說明。

裝好之後兩步就夠：

1. 跑 [`/setup-pstack`](https://github.com/cursor/plugins/blob/main/pstack/skills/setup-pstack/SKILL.md)，選 reasoning 預算，再指定各角色用哪個模型。
2. 需要嚴謹工程時用 [`/poteto-mode`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md)。

不確定該用哪個 skill，問 [`/poteto-help`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-help/SKILL.md)。第一次實作可以照 [pstack guide](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/README.md)，從設定、下 prompt，走到驗證和過夜執行。

預設分工：功能、重構、修 bug、效能、hillclimb 這類 code delegate 走 Grok；最難的改動、散文和判斷走 Opus 5.5。預設審查面板是 Opus 5.5 / Grok。`/setup-pstack` 可以改。規則檔若還釘著舊預設，把那些角色列刪掉，或整份刪掉再跑一次。重跑時，跟預設不同的角色會留著。

# 🧅 /poteto-mode 在做什麼

從 `/` 選單先選 `/poteto-mode`，再打任務，skill 才會掛在這則訊息上。Mac 用 Option+Enter、Windows 用 Alt+Enter，會把它收成 custom mode，之後每一輪都帶著，直到你離開。普通 Enter 只掛這一則。

它做三件事：對上 playbook，把步驟原樣抄進待辦；步驟需要時再呼叫其他 skill；回覆寫給使用者和維護者，並把廢話收掉。

README 列了 23 份 playbook。常用的大概是這幾種：

| playbook | 什麼時候用 |
| --- | --- |
| investigation | 只讀。這段怎麼運作、為什麼做成這樣 |
| bug fix | 先重現，再找根因，用執行期證據修 |
| perf / hillclimb | 對基線量測；hillclimb 是單一指標持續爬坡，接受的改進各一個 commit |
| runtime / trace forensics | 活著的症狀，或已經抓下來的 profile、trace、heap |
| feature / refactoring / prototype | 新行為、不改行為的結構調整、用完即丟的對照草稿 |
| visual parity | 兩套 UI 要做到像素級一致 |
| eval | 盲測 skill 或 prompt 改動對 agent 行為的影響 |
| babysit / shipping | 把 PR 或 stack 推到可合併；獨立驗證綠燈之後再由下往上落地 |
| autonomous run / orchestrate | 長任務不停，或一個協調對話管多天、多層 PR |
| autopilot-full / autopilot-stack | 多個獨立 PR 各有負責人並反覆驗證，或一條線性 stack 留給人審 |
| session pickup / pause safely | 接手進行中的工作，或先乾淨暫停 |
| opening a pr | 其他 playbook 收尾時開 PR：小而有序的 commit、Conventional Commits 標題 |

範例長這樣：

```text
/poteto-mode this pr has a subtle bug where the scroll drifts every 750ms even when idle. repro
first, then fix and verify.
```

過夜：

```text
/poteto-mode i'm going to bed. land the stack even if ci flakes. i want everything merged by
morning.
```

README 也寫它跟 Cursor 的 `/loop` 搭得很好，可以跑好幾個小時，流程仍走同一套檢查。

# 💬 Poteto Mode 常用提示範例

上面的 `/poteto-mode` 是 Cursor 寫法。Codex 若已安裝社群移植版 [pstack-for-codex](https://github.com/Aqua-123/pstack-for-codex)，提示要寫 `$poteto-mode`，或 `$pstack-for-codex:poteto-mode`。不要把 Cursor 的斜線指令貼進 Codex。

本機安裝文件是 0.4.0，README 寫它追的上游是 pstack 0.15.24，和本文前面 Cursor 目錄的 0.15.29 不是同一份。技能數量、hook、模型設定都以安裝版的 `README.md` 與 `docs/codex-adaptation.md` 為準，不要假設和 Cursor 上游完全相同。

提示寫目標、限制，以及可以檢查的完成條件。Poteto Mode 會自己選 playbook，不必手動點一串 skills。換題目時在同一則開頭加 `new task`。只想先起草提示、還不開工，用 `$poteto-help`。

簡單問答、改一句文案、一步就能改完的小修改，直接下指令。不必每次都開 Poteto Mode。

它不能取代你的授權。多步驟任務要把只讀範圍、要跑的測試，以及能不能 commit、push、merge 寫清楚。沒跑過的測試或驗證，不能在回覆裡寫成已通過。父任務仍掌握整合、對外寫入、提交、推送和最終結論；子 agent 的報告是證據，不是完成。

### 1. 只讀調查

```text
$poteto-mode new task. 說明 <子系統> 在 <情境> 下怎麼運作，以及為什麼做成這樣。只讀，不要修改程式碼、不要開 PR。完成條件：結論要指到檔案與呼叫路徑，未知的部分單獨列出。
```

### 2. Bug 修復

```text
$poteto-mode <症狀：誰、在什麼操作後、看到什麼>。先重現，再找根因，再修。修完跑 <回歸測試或手動步驟>，並附上通過與否的輸出。不要 commit、不要 push。
```

### 3. 新增功能

```text
$poteto-mode 新增 <行為>。必須保留：<既有行為 1>、<既有行為 2>。驗收：<可觀察的結果>。完成前跑 <測試命令>。不要擴到這份範圍以外，不要 commit、不要 push。
```

### 4. 效能問題

```text
$poteto-mode <操作> 目前約 <現況，例如耗時或 CPU>。先在 <環境與命令> 建立量測基準，再改，然後用同一組條件比較前後。沒有前後數字就不要宣稱變快。不要 commit。
```

### 5. 設計或 UI 原型

```text
$poteto-mode 比較 <方案 A> 和 <方案 B>，用來決定 <哪個設計或 UI 問題>。原型各自放到獨立輸出目錄，不要改正式程式。比較完列出差異和取捨，等我決定再進正式實作。
```

# 🧩 其他 skill，以及 24 條原則

多數時候不用自己點。`/poteto-mode` 會在步驟需要時叫 `/how`、`/why`、`/architect`、`/arena`、`/swarm`、`/interrogate`、`/unslop`、`/no-comments`、`/tdd` 和原則檔。

想單獨用的話，方向大致是：

- `/how`、`/why`、`/teach`：子系統怎麼走、為什麼做成這樣。`/why` 會在執行時找可用的 MCP，並行查版控、issue、長文、即時聊天、觀測、錯誤追蹤、分析倉。`/teach` 把 how 和 why 編成一份說明，一張圖接一張圖。
- `/recall`、`/ketchup`：從自己的對話和共用紀錄還原現況；或只看這輪聊天從上一則訊息之後改了什麼、還有哪些項目在等你決定。
- `/sharpen`、`/in-your-own-words`：前者把 prompt 寫深，交回改寫後的 prompt，不代做；後者先用你的話複述目標和問題。兩者都只在你打出指令時跑。
- `/blast-radius`：小改動可能打到哪。它要求那個「所以安全」的事實來自跑過的程式，不是口頭保證。
- `/arena` 是同一件事開 N 次再挑好的部分；`/swarm` 是不同切片各一名 worker，最後一份報告。
- `/interrogate` 拿 diff 給不同模型試著打穿，含嚴格的程式品質角度。
- `/tdd`：有便宜的本地測試時，先寫會失敗的測試再修。
- `/benchmark-checklist`：數字拿去報告或據此改程式之前，先查瓶頸、調參、誤差、重複跑、以及這數字是否真的是端到端的那件事。
- `/no-comments` 會叫出唯讀的 Comment Sicko，把註解清掉再審。
- `/automate-me` 從你近期逐字稿草擬一份 `<你的名字>-mode`，底下仍走 pstack。
- `/reflect` 把做完的長任務收成 skill 修改；`/correct` 從歷史裡挖重複犯錯的類型，優先改架構、型別、lint、CI、測試，文件放最後。
- `/show-me-your-work` 把決策寫進可提交的 TSV。
- `/create-verification-skill` 與 `/maintain-verification-skill`：專案沒有可腳本化的行為證明時，生一份本地 verify skill；地圖漂了就做一輪對源碼再加一輪實機，最多一個 PR 的已證實修正。
- `/figure-it-out`：現成 playbook 都不貼時，為這次任務設計一份可稽核的流程。

原則有 24 條，`poteto-mode` 開頭會讀索引。分四組：core、architecture、verification、delegation，外加 meta 的 `encode-lessons-in-structure`（能寫成 lint、檢查或腳本的，就不要再堆一段說明文字）。

core 裡幾條最常被引用：能刪就刪（laziness-protocol）；先把資料結構定對（foundational-thinking）；同一前提的修法連續失敗時，先把前提寫下來打它（attack-the-premise）；先減再加；讀者從問題到答案要穿過的層數要算。verification 則要求對真實產物驗證，而不是「能編譯」或代理自己說做完了。

委派時有兩條硬的：大量原料丟給 subagent，主線只留摘要（guard-the-context-window）；能做完再給人改方向，只有不可逆操作才先問（never-block-on-the-human）。

Subagent 用 `subagent_type: "poteto-agent"`。它會先把 `poteto-mode` 整份讀完，含原則索引。換成 generalPurpose 就會跳過這步，後面容易漂。不要叫 poteto-agent 自己去跑 playbook，playbook 留在收到 `/poteto-mode` 的那個對話。

# ⚠️ 沒有包進來的東西

`/deslop`、`control-cli`、`control-ui` 在 `cursor-team-kit`，不在這包。`/create-skill` 是 Cursor 內建。Cursor 自己的 `/autopilot` 會看 PR；在 poteto-mode 裡，查 PR 狀態走 babysit playbook。

作者寫得很明白：她不相信先寫一份大計劃。Cursor 已有 Plan Mode，要計劃也可以，但 pstack 的預設不是規劃 skill。她的原話是 the best spec is code。

`automations/benny` 是休眠的自動化包，不是 slash skill。它會分流 Slack 的問題回報，對確認過的 bug 用真實 UI 證據重現並修。設定指向 `automations/benny/FOR_AGENTS.md`，會把包複製到目標倉庫的 `.cursor/automations/benny/`。這條只在 Cursor Automations 上跑。
